Masalah yang diselesaikan

Hasil observasi dan wawancara dengan guru kelas VI SLBN Cicendo menunjukkan tiga hambatan. Klik tiap masalah untuk melihat dampaknya dan jawaban dari sisi backend.

1Susah menarik perhatian siswa tunarungu

Dampak

Siswa tidak bisa dipanggil dengan suara. Guru harus mendatangi satu per satu, dan pembelajaran terhenti sementara.

Jawaban backend

Endpoint /tegur dan /panggil mendorong perintah lewat WebSocket ke pin siswa yang dituju. Pin bergetar dan menyala tanpa menunggu permintaan.

2Presensi masih manual

Dampak

Guru memanggil dan mencatat kehadiran satu per satu. Waktu belajar terpotong setiap pagi.

Jawaban backend

Endpoint /presensi mencatat kehadiran beberapa siswa sekaligus dengan tanggal dan jam WIB, lalu memberi konfirmasi getar satu kali ke pin.

3Tidak ada catatan aktivitas

Dampak

Sekolah dan orang tua tidak punya data berapa kali seorang anak ditegur, dipanggil, atau hadir.

Jawaban backend

Setiap kejadian masuk ke tabel aktivitas. Dari sana backend membuat laporan harian, laporan rentang tanggal, grafik, dan ekspor PDF, dengan akses sesuai peran.

Analogi. Backend itu operator telepon sekolah. Guru bilang "sambungkan ke siswa nomor 4", operator mencari sambungannya, menghubungkan, lalu mencatatnya di buku log. Bedanya, semua ini selesai kurang dari satu detik.

Arsitektur dan perjalanan satu perintah

Aplikasi hanya bicara dengan backend. Backend memeriksa hak akses, mencatat ke database, lalu meneruskan perintah ke pin. Putar langkah demi langkah di bawah ini.

Flowchart

Tiga alur logika di dalam backend, ditambah jalur dari kode sampai server produksi. Alur kerja utama ada di stepper pada bagian Arsitektur.

Login tiga peran

Setiap peran dicari dengan identitas berbeda, lalu password diperiksa dengan bcrypt. Login yang berhasil dicatat di login_history.

flowchart TD
    A([Pengguna isi login]) --> B{Pilih peran}
    B -- Admin --> C[Cari berdasarkan email]
    B -- Guru --> D[Cari berdasarkan NIP + kode kelas]
    B -- Orang Tua --> E[Cari berdasarkan NIS anak]
    C --> F{Pengguna ditemukan?}
    D --> F
    E --> F
    F -- Tidak --> G[400: User tidak ditemukan]
    F -- Ya --> H{Password cocok? bcrypt}
    H -- Tidak --> I[400: Password salah]
    H -- Ya --> J[Catat ke login_history]
    J --> K[Terbitkan token JWT, berlaku 1 jam]
    K --> L([Masuk ke halaman sesuai peran])

Penjaga pintu (middleware)

Setiap permintaan ke endpoint terlindungi melewati tiga pemeriksaan sebelum menyentuh controller.

flowchart LR
    R[Request masuk] --> M{Ada token?}
    M -- Tidak --> X1[401: Token tidak ada]
    M -- Ya --> V{Token valid?}
    V -- Tidak --> X2[401: Token tidak valid]
    V -- Ya --> P{Peran sesuai?}
    P -- Tidak --> X3[Akses ditolak]
    P -- Ya --> OK[Lanjut ke controller]

Mendaftarkan pin baru lewat QR Code

QR di pin berisi alamat IP. Backend memeriksa apakah IP itu sudah dikenal, lalu memasangkannya dengan identitas siswa.

flowchart TD
    A[Guru scan QR di pin, berisi alamat IP] --> B[POST /api/admin/device/register]
    B --> C{IP sudah ada di tabel devices?}
    C -- Sudah --> D[Tampilkan info siswa pemilik pin]
    C -- Belum --> E[Simpan perangkat baru]
    E --> F[Guru isi nama, NIS, kelas]
    F --> G[POST /api/admin/device/tambah-siswa]
    G --> H[Simpan siswa dan tandai perangkat terdaftar]

Dari kode ke server produksi

Dikembangkan dengan MySQL lokal (XAMPP), lalu database dimigrasi ke Railway. Setiap push ke branch utama membangun ulang container otomatis.

flowchart LR
    A[Laptop + MySQL lokal XAMPP] -- git push --> B[GitHub]
    B -- build otomatis --> C[Railway: Docker node 18 alpine]
    D[(MySQL Railway hasil migrasi)] --- C
    C --> E[URL publik REST dan WSS]

Refleksi

Yang belum sempurna

  • Packet loss 16% saat koneksi ke database tidak stabil. Butuh penguatan koneksi dan retry.
  • Lonjakan response time pada beban sangat tinggi. Query laporan perlu dioptimasi.
  • Kualitas komunikasi turun jika pin lebih dari 6 m dari Wi-Fi. Ini faktor jaringan, bukan pemrosesan server.

Yang saya pelajari

  • Merancang REST API dan WebSocket dalam satu server.
  • Keamanan dasar: hash password, JWT, middleware, menyembunyikan rahasia.
  • Zona waktu server cloud (UTC) dan cara menjaga tanggal tetap WIB.
  • Membaca hasil JMeter: titik jenuh, throughput, error rate.
  • Alur Docker, GitHub, dan Railway.

Rencana berikutnya

  • Reconnect dan antrean perintah untuk pin yang sedang offline.
  • Caching pada endpoint laporan.
  • Rate limiting dan validasi input yang lebih ketat.
